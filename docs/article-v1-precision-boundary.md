# 确定性 AST 图谱在真实仓库上的精度边界——CodeCompass 1.0 的度量、修复与失败面

> CodeCompass 是一个给 coding agent 的**确定性代码事实层**：17 个 MCP 工具、零 LLM、对源码只读，每个结论都带 `file:line` 锚点。1.0 的核心承诺不是"功能多"，而是一句可证伪的话：**它的假阳性率被度量，且本文把度量过程、修复过程和到不了 0 的原因全部摊开**。
>
> 本文所有数字可由仓库内命令复现（见文末），三条样本仓全部是公开开源项目（[lazygit](https://github.com/jesseduffield/lazygit)、[spring-petclinic-microservices](https://github.com/spring-petclinic/spring-petclinic-microservices) 与 CodeCompass 自举），不含任何私有仓数据。

## 0. 问题：agent 读大仓时，最贵的不是 token，是"信不过"

几千文件以上的仓库里，让 LLM 直接读代码找"谁调用了这个函数 / 改这个路由会影响什么"，成本高且不可复核。CodeCompass 的路线是把这一类**大规模确定性查找**从 LLM 手里拿走：`@lezer` 语法树建图 → 调用链 / 反向依赖 / 影响面 / 候选扫描，静态解析不到的位置显式标记 **Static Analysis Break**，绝不静默编造。

这条路线成立的前提是一个字：**准**。假边比没有边更糟——agent 会顺着一条猜出来的调用链走得很远。所以 1.0 的主战场不是加功能，而是把"精确"放上真实仓库的刻度尺。

## 1. 度量先行：没有刻度尺就没有优化

第一件事不是修 bug，是建 harness（`scripts/precision/scan_precision.ts`）：索引 → 五桶扫描 → 固定种子抽样 → 逐条人工判定入档 → `--score` 复算。一条命令跑完三仓：

```bash
npm run precision                # 索引三仓并输出五桶 + top-10 抽样
npm run precision -- --score self lazygit petclinic   # 从判定文件复算 M1
```

**M1 的口径**：孤儿桶（"零静态调用者"候选）按位置取前 10 条，**逐条人工核验**是真死代码还是误报。前 10 不是随机样本——它天然代表"最显眼"的残余，是 agent 实际会看到的那批。

第一课在这里就出现了：v0.21 留下的"43% / 31% / 83% 假阳性率"三个数字，复核后确认是**孤儿占符号比（水位）**，不是假阳性率。两个口径混用让我们误以为问题已被度量过。真实起点是：**三仓 top-10 假阳性率 100%（10/10）**。

## 2. 修复链：每一轮先归因，再动手

### 2.1 七个根因，−42%

TS 适配器当年用纯 JS 方言解析，把类型注解和 JSX 全判成语法错误；裸调用丢边、JSX 使用无边、局部变量不记类型、DI 注解白名单不全……七项修完，self 仓孤儿 **1182 → 689（−42%）**，petclinic **152 → 45（−70%）**。

### 2.2 Go receiver 绑定：票面假设被实测推翻

修 lazygit 前的假设是"跨文件类型引用是主因"。探针实测推翻了它：真主因是**同文件**的两件事——`:=` 短声明与 `var` 是同一种 AST 节点但没有 `VarSpec`，导致声明类型恒读不到；以及裸调用被错误继承所属类型的 selfType。修完 lazygit 孤儿 **3229 → 2851（−11.7%）**。

更重要的是边级账：per-repo 包表补上跨文件定型后，孤儿只再降 18 条，但 **800 条 `dynamic` 边变成带类型的 receiver、498 条断点变成可解析**——孤儿桶只看得见"目标此前无其他调用者"的一小撮，**调用链才是产品核心**。只盯桶上数字会严重低估这类工作。

### 2.3 ADR-0018：58% 的"假阳性"其实是问错了问题

lazygit 全桶 2805 条里 1618 条（58%）不是引擎不行：类型声明 623（类型没有"调用者"概念）、接口方法声明 375（契约成员的正常形态）、接口实现方法 620（Go 接口多实现时按确定性纪律必须保持 dynamic）。裁决是**收窄桶语义而不是补边**：桶从此只声称"可调用符号中的零静态调用者"，且每条排除规则按计数回报（census 守恒等式机器核对）。lazygit **2805 → 1807**。

### 2.4 跨文件类型表 + 接收者定型：self top-10 的 `RepoQAClient.*` 从 7 条到 1 条

self 仓 top-10 里 7 条是前端 API client 的方法。逐族归因（每族先做"先红后绿"的归因探针）：`Pick<T,K>` 工具类型与具名接口成员、`useMemo` 工厂、跨文件 hook 返回类型、回调参数按被调方签名定型……逐族落地后 **7 条降到 1 条**（唯一剩下的 `getRepo` 是真死代码）。

### 2.5 按名回退假边：1014 条"猜出来的边"归零

评审发现解析器收尾的按名回退把两种情况混为一谈：**没有接收者信息**（裸调用，按名解析是既定能力）与**声明了接收者类型但索引不认识**（外部类型如 `Error`、`strings.Builder`）。后者此前会**用一个同名方法猜出一条边**。先量后修：三仓 **1014 条**这样的边（self 438 / lazygit 575 / petclinic 1），修后归零。典型如 `Error.constructor → HarnessRegistry.constructor`（356 条）——两个毫无关系的类被一个方法名缝在一起。

### 2.6 汇总

| 刻度 | 起点 | 1.0 |
|---|---|---|
| self top-10 假阳性率（M1） | 100% → 90%（09-20 首次破 100%） | **40%（4/10）** |
| self 孤儿水位 | 1182 | **243**（−79%） |
| lazygit 孤儿 | 3288 | **1828** |
| petclinic 孤儿 | 152 | **13**（−91%） |
| M2 桶污染（vendor/测试夹具入榜） | 有 | **0/0/0** |
| 合成 eval（97 题 / 10 bucket） | — | Recall@5 全 100%、幻觉 0% |

## 3. 失败面：为什么到不了 0

这是本文最重要的一节。1.0 的 M1 是 40%，不是 0%，而且**有些部分永远不该是 0**。

**① lazygit / petclinic 的 top-10 假阳性率仍是 100%——但这是问错了问题。** 它们的残余由类型声明（没有"调用者"概念）和 Go 隐式接口实现方法（620 条）构成。Go 的接口满足是隐式的，静态分析按 ADR-0002（解析不到不猜）本就应该保持 dynamic——把这些报成"零调用者"才是错的，把它们排除出候选才是对的。桶语义收窄后这 620 条被显式登记为结构性噪声，而不是被"修掉"。

**② self 剩余 4 条假阳性分属两族机制缺口**：DOM 事件值引用（`window.addEventListener('keydown', onKeyDown)` 是标识符引用，不是调用表达式，本就不该产生"调用边"）和成员链接收者（`streamRef.current?.stream.close()`，前缀链静态不可定型）。两族都有机制登记，但没有为 1.0 强行立票——先有度量，再有战役。

**③ 1.0 也带着 6 条真阳性**：`getRepo` 与 `ChatMergeClient` 的五个方法，生产代码零调用、只在自己仓库的测试替身里以对象字面量出现。这是真死代码（Web 面清理清单），1.0 没有为了数字好看先删掉它们——它们留在桶里，恰是桶在做它该做的事。

**④ 三次"改了没用"的静默哑弹**，比崩溃难抓得多：
- lezer 的 `SyntaxNode` 每次访问都新建包装对象，`argumentNodes(call).indexOf(node)` **恒为 -1**——一处绑定静默地从未生效，直到逐文件 before/after 探针对照才发现；
- 单测 fixture 里的多行模板串未被掩码，`interface RepoContextValue` 的幻影声明与真声明同名异内容，跨文件表的歧义规则（正确地）丢了真表项——**两次**被自己仓库的测试文件污染测量；
- 具名接口的成员表为空时（方法型契约没有 `name: type` 成员），一个 truthy 空 Map 让参数绑定走进空分支且不再回头。

**⑤ 一行"修复"能让事情更糟**：掩码器不掩多行模板串，一行加宽 backtick 分支就能修——实测它让注释里的反引号与远处的反引号配对，**中间的真注释文字反而不被掩码**，本仓掩码器当场把自己的注释变成了幻影声明。配对只有在注释被排除之后才可信，这是状态机问题，不是正则强度问题。

**⑥ 代理指标会与真实质量反向**：移除 1014 条假边后，孤儿桶**变大**了（self 237 → 246、lazygit 1807 → 1828）——那些只靠假边"被调用"的符号现在真的零调用者了，假阴性一侧变得可见。如果只盯桶上读数，这一步会被当成回退。

## 4. 工程底座（一段带过）

支撑上面所有数字的是一套可复现的门禁：e2e closeout gate **71 项断言**（含版本五处一致性、MCP 握手版本棘轮、精度棘轮、普查守恒真等式）、97 题合成 eval（九桶 Recall@5 全 100%、幻觉 0%）、每个发布版本必过的双轴 code-review（两轴并行 sub-agent，Standards / Spec 分离）、以及大规模索引基线 **26.3s / 438MB**（1.0 目标 ≤30s / ≤500MB，达标）。过程中修过的一个真 bug 值得一提：优雅关闭时 WebSocket 让进程挂死，三轮破案才定位——这类问题 330 个单测全绿也抓不住，因为 mock 不校验关单时序。

## 5. 适用与不适用

**适用**：几千文件以上的仓库；给 agent 提供"谁调用它 / 改这里影响什么 / 这符号还有没有人用"的确定性底座；CI 里的架构影响面门禁；onboarding 路线（三条 tour 从真实锚点自动生成）。

**不适用**：架构判断与设计评审（那是 agent 的读码工作）；需要写回代码的场景（只读，补丁由宿主侧 agent 生成）；把"零静态调用者"直接当成"可安全删除"——桶声称的只是事实，处置是人的决定。

**时间窗口的诚实声明**：若宿主平台把跨语言调用链与逐字锚点做进原生索引，这条路线的独立价值会迅速收窄。1.0 的锚点在此窗口内落定，这也是它现在发布而非继续打磨的原因。

## 6. 复现

```bash
# 试用（Node 24）：
npx @codecompass/cli mcp /path/to/your/repo     # stdio MCP，17 个 codecompass_* 工具

# 精度（三仓开源样本，一条命令，判定文件入档）：
npm run precision                                # 索引三仓 + 五桶 + top-10
npm run precision -- --score self lazygit petclinic   # 从判定文件复算 M1

# 合成 eval（97 题 / 10 bucket）与门禁（71 项）：
npm run eval
npm run e2e
```
